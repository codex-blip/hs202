PROJECT CONTEXT

Project name: Sahakar Sahayak
Suggested report title: “Sahakar Sahayak: A Multilingual Cooperative-Services Information and Guidance Assistant”

Purpose: Sahakar Sahayak is a public-interest prototype intended to make information about cooperatives and related agricultural services easier to discover, understand, and navigate. It aims to help users explore cooperative governance, Primary Agricultural Credit Society (PACS) services, crop insurance (including PMFBY), financial literacy, government schemes, legal information, and grievance routes. It is an informational guide, not a government service, legal/financial adviser, eligibility assessor, or complaint-submission authority.

Problem framing: relevant cooperative and agricultural information can be difficult for users to find, interpret, verify, and navigate across topics, languages, jurisdictions, and official channels. Present this as the project’s identified design problem and rationale, not as a quantified or field-validated claim. Explain that any claims about the severity or prevalence of the problem require user research and authoritative evidence.

CURRENT PROTOTYPE — IMPLEMENTED CAPABILITIES
- React and TypeScript frontend built with Vite; FastAPI backend in Python.
- Multilingual AI chat can answer in the latest user message’s language when the configured model supports it. Language quality is model-dependent, not guaranteed.
- Interface language switching is currently documented for English, Hindi, and Punjabi.
- Topic browsing for cooperative governance, crop insurance/PMFBY, PACS and cooperative services, financial literacy, schemes, legal information, and grievances.
- Scheme-guidance wizard uses demonstration records to show example requirements, documents, citations, limitations, and suggested next steps. It does not determine eligibility.
- Grievance page provides example routes and preparation checklists; it does not file, adjudicate, or track complaints.
- Voice input is transcribed through Sarvam; the user can review the transcript before sending it. Sarvam text-to-speech can play assistant answers. The documentation says playback supports 11 languages and text up to 2,500 characters; audio recording and upload limits are documented in the README.
- Recent conversation history is stored in browser local storage. Up to 12 recent turns may be sent as chat context.
- Users can attach up to five PDF/DOCX documents of up to 20 MB each per conversation. PDF and DOCX text are extracted and indexed in local SQLite FTS5. Chat retrieves up to five matching chunks with a combined 9,000-character limit and sends them as untrusted context. Answers can cite uploaded filenames and PDF page numbers when available. This is basic lexical retrieval over user-provided documents, not a maintained official-source knowledge base. Scanned-PDF OCR depends on separately installed Tesseract and language data.
- Frontend mock mode is available. The project can also use its FastAPI endpoints and Sarvam, subject to configuration.
- Useful API routes documented in README include /api/health, /api/chat, /api/documents, /api/audio/transcriptions, /api/audio/speech, /api/schemes/guidance, /api/grievances, and /api/sources.

KEY LIMITATIONS AND PLANNED WORK
- There is no maintained, human-reviewed official knowledge base, source-ingestion/review process, jurisdiction/date-aware retrieval, multilingual semantic/hybrid search, source expiry management, or verified citation system for general chat.
- Scheme and grievance records are static examples. Current rules, deadlines, local eligibility, routes, or availability must be checked with the responsible official authority.
- General chat responses are AI-generated and may be incorrect. The user must verify consequential information with official sources or qualified professionals.
- The prototype does not have user authentication. The README warns against exposing the backend publicly with sensitive uploads until document routes are protected by authenticated user ownership.
- User interface translations and speech quality/accessibility across languages and devices remain areas for improvement. Low-bandwidth and assisted-use support, user feedback for outdated answers, and stronger accessibility are planned.
- The planned source-grounded approach is to create an approved source catalog with issuing authority, canonical URL, jurisdiction, language, publication/effective dates, last-checked date, reviewer, and active/expired status; ingest approved material with page/section boundaries; start with evaluated FTS5 and add multilingual embeddings only if evaluation demonstrates a need; filter by jurisdiction/date; keep citations tied to retrieved metadata; instruct the model to treat documents as untrusted; abstain when evidence is insufficient; and maintain a reviewed question set and update cadence.
- Keep uploaded-document retrieval separate from any future trusted public-source retrieval. Do not imply that embedding/vector infrastructure is currently part of the project.
